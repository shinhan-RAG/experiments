# Collection Index JSON 문서 선택 실험 결과

> 실행일: 2026-08-03  
> 범위: 하나의 컬렉션 안에서 질의에 맞는 문서 1개 이상 선택  
> 제외: 문서 내부 Chunk/Element 검색, Vector Search, 답변 생성

## 1. 목적

상품 1,220개, 문서 9,417개가 포함된 컬렉션에서 구조화된
`collection_index.json`이 파일명만 사용하는 기준선보다 문서 선택 성능을 개선하는지 확인한다.

이 실험에서 JSON은 LLM 프롬프트에 통째로 넣지 않는다. 검색 프로그램이 JSON 필드를 검색 표현으로
변환하고 Top-k 문서를 반환하는 방식으로 평가한다.

## 2. 실험 데이터

| 항목 | 값 |
|---|---:|
| 상품 | 1,220개 |
| 문서 | 9,417개 |
| JSON 크기 | 5,744,495 bytes (약 5.48 MiB) |
| JSON 생성 시간 | 0.43초 |
| 평가 QA | 582문항 |
| 평가 시간(3조건) | 63.26초 |

QA는 이전 `doc_find_ab3.py` 실험과 동일한 코드와 `seed=7`로 생성된 문항을 고정 파일로 저장해
재사용했다. 기준선 결과가 이전 실험과 정확히 일치하는 것으로 동일 QA 재현을 확인했다.

| 질의 유형 | 문항 수 | 예시 |
|---|---:|---|
| 최신 정본 | 134 | `OO 최신 판매약관` |
| 연도+종류 | 216 | `OO 2018년 사업방법서` |
| 종류만 | 232 | `OO 공시약관 보여줘` |
| 전체 | 582 | |

## 3. Collection Index 스키마

문서 선택에 사용한 주요 정보는 다음과 같다.

```text
product_name
title
flags
kind_hints
doc_type
effective_date
is_representative
```

`title`은 파일명에서 날짜, 구분자, 버전 suffix 등의 노이즈를 제거한 정규화 문서명이다.

기준 JSON에는 검색 결과와 원문을 연결하기 위해 다음 정보도 보존한다.

```text
collection_id
product_id
document_id
file_name
file_path
version
date_granularity
date_confidence
```

## 4. 비교 조건

| 조건 | 검색 표현 |
|---|---|
| 파일명 기준 | 상품 폴더명 + 원본 파일명 |
| 새 JSON Index | 상품명 + 정규화 title + 상품 속성 + 문서 종류 + 날짜 + 정본 표시 |
| 요약 | 상품명 + 원본 파일명 + 상품 단위 LLM 요약 |

요약 조건은 비교군이며 Collection Index 스키마 필드로 채택한 것이 아니다.

## 5. 결과

### 전체 결과

| 조건 | Top1 | Top5 | 파일명 대비 Top1 | 파일명 대비 Top5 |
|---|---:|---:|---:|---:|
| 파일명 기준 | 52.6% (306/582) | 81.6% (475/582) | - | - |
| 새 JSON Index | **70.4% (410/582)** | **90.5% (527/582)** | **+17.9%p** | **+8.9%p** |
| 요약 | 50.3% (293/582) | 77.1% (449/582) | -2.2%p | -4.5%p |

### 질의 유형별 결과

| 질의 유형 | 파일명 Top1/Top5 | 새 JSON Top1/Top5 | 요약 Top1/Top5 |
|---|---:|---:|---:|
| 최신 정본 | 13.4% / 67.2% | **54.5% / 85.1%** | 11.2% / 61.2% |
| 연도+종류 | 56.9% / 83.8% | **74.1% / 94.4%** | 56.9% / 82.4% |
| 종류만 | 71.1% / 87.9% | **76.3% / 90.1%** | 66.8% / 81.5% |

### 통계 검정

파일명 기준과 새 JSON Index의 paired McNemar exact test 결과다.

| 지표 | 파일명만 성공 | JSON만 성공 | p-value |
|---|---:|---:|---:|
| Top1 | 15 | 119 | 2.87e-21 |
| Top5 | 2 | 54 | 4.43e-14 |

이 QA에서는 새 JSON Index의 개선이 통계적으로 유의하다.

## 6. Ablation: 성능이 오른 이유

새 JSON Index에서 정규화 `title`과 정본 계산 방식을 분리해 확인했다.

| 조건 | Top1 | Top5 |
|---|---:|---:|
| 새 JSON 전체 | **70.4%** | **90.5%** |
| `title` 제외 | 63.4% | 88.7% |
| 최신일 복수 정본 대신 단일 정본 | 70.4% | 90.5% |
| `title` 제외 + 단일 정본 | 63.6% | 88.8% |

정규화 `title`은 Top1 약 **+7.0%p**, Top5 약 **+1.9%p**에 기여했다.
동일 최신일 문서를 복수 정본으로 표시한 변경의 전체 영향은 거의 없었다.

따라서 새 결과가 이전 구조화 실험보다 높은 주된 이유는 JSON 포맷 자체가 아니라,
파일명의 날짜·기호·버전 노이즈를 제거한 문서별 정규화 `title`을 검색 표현에 추가했기 때문이다.

## 7. 해석

확인된 내용:

- 문서 종류, 정규화 날짜, 최신 정본 표시는 문서 선택에 유효하다.
- 정규화 title은 특히 Top1 문서 선택을 개선한다.
- 상품 단위 요약은 개별 파일을 구분하지 못하고 BM25 노이즈를 늘린다.
- 5.7MB JSON 생성은 0.43초로 적재 생성 비용이 낮다.

확인되지 않은 내용:

- JSON 문법 자체가 검색 성능을 높인 것은 아니다.
- LLM이 key lookup 도구로 JSON을 조회하는 에이전틱 성능은 아직 측정하지 않았다.
- Vector Search는 수행하지 않았다.
- 실제 사용자 질의에서 동일한 개선 폭이 유지되는지는 확인하지 않았다.

## 8. 한계

1. QA는 실제 사용자 로그가 아니라 파일 시스템 사실에서 만든 합성 질의다.
2. 질의에 상품명, 연도, 문서 종류가 직접 포함되어 정규화 필드와 어휘 정렬이 높다.
3. 이 결과는 구조화 필드의 회귀 테스트로는 유효하지만 운영 효과 크기로 일반화할 수 없다.
4. 요약은 상품 단위 요약이므로 문서별 요약과 다른 조건이다.
5. 현재 평가는 BM25 검색이며 LLM 도구 호출·latency·token 비용을 포함하지 않는다.

## 결론

동일한 582개 QA에서 새 Collection Index의 구조화 필드를 사용하면 파일명 기준 대비
Top1은 **52.6%에서 70.4%**, Top5는 **81.6%에서 90.5%**로 개선됐다.
개선의 가장 큰 추가 원인은 정규화된 문서 `title`이다. 다음 단계는 실제 사용자 질의와
key lookup 도구를 사용한 에이전틱 문서 선택 실험이다.
