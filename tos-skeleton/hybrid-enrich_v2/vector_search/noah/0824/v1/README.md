## 2. v6 → v7 변경점 (요구사항 반영)

**1. required 그룹 문항당 최대 5개.**
6개 이상이던 문항은 초과분을 **삭제하지 않고** 명세 §2의 `supporting`으로 강등했다. 근거는 파일에 그대로 남고 채점에서만 빠진다. 덕분에 모든 문항의 R@5 산술 상한이 **1.0000**이 된다(v6는 .9431이었다).

어느 5개를 required로 남길지는 **인간이 쓴 `정답(종합)` 본문과의 문자 bigram 겹침(`usage`)** 으로 정했다 — "답을 쓰는 데 실제로 쓰인 근거"가 required다. 동점은 인용 순서, 그다음 길이.

> 검증: 선별 기준을 usage / 인용순서 / 길이순으로 바꿔 A/B 한 결과 R@5 가 동일했다. 그룹이 5개를 넘는 문항이 34개뿐이라 기준 선택은 병목이 아니다.

**2. 빈 배열 금지.**
조가 안 잡히는 그룹 제거, `groups`/`members`/`jos`가 비는 레코드 제거, 값이 없는 키(`scopes`, `task_type`, `scope` 등)는 아예 쓰지 않는다.

**3. 답안지 질문 중복 제거.** CSV에 같은 질문이 5쌍 들어 있었다(no 335/342 등). qid당 1행만 남기되 정위 인용이 많은 쪽을 채택했다.

## 4. 실측 — 융합(meta+tag) 재실행 결과

**2026-08-24 신규 실행.** gold v7 train n=184, 질문태그 `qtags_luna.jsonl`(codex CLI / gpt-5.6-luna, 184/184 parse_ok),
임베딩 `dragonkue/BGE-m3-ko`, 태그 `tags_u2_rules.jsonl`, **깊이 무제한**(limit·meta_top_k 2000, union 무제한).
아카이브 예측의 top-40 절단 문제를 없앤 값이다. 평가 대상은 **융합 arm 하나**다.

융합은 **조 단위로 접은 뒤** RRF(k=60, 1:1). strict 기준.

| R@1 | **R@5** | R@10 | R@20 | R@40 | R@200 | **R@inf** | suff@5 | suff@10 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| .1534 | **.4068** | .5312 | .6151 | .6971 | .8870 | **.9855** | .2772 | .3913 |

두 번의 수정을 거친 값이다: 정위 결함 수정(§4.1) **.2563 → .3738**, 조 단위 융합(§4.2) **.3738 → .4068**.
strict/lenient 는 동일해졌다 — 동일 인용의 모든 출현을 OR 멤버로 넣으면서 160자 접두 확장이 더 보탤 것이 없다.

**required 개수별 R@5**: 1개(77문항) .5195 | 2개(45) .4000 | 3개(26) .3846 | 4개(10) .2250 | 5개(26) .1769

**그룹 위치**: top-5 **33.3%** / 6~400위 **56.4%** / 400위 밖 10.4%. `R@inf` .9855 이므로 거의 전부 잡히긴 한다 — 순위만의 문제다.

### 4.1 정위 결함과 수정 (2026-08-24)

초판 빌더는 인용문이 원문에 정확일치하지 않을 때 **앞 25~40자 앵커의 첫 번째 출현**을 정답 위치로 찍었다.
약관은 같은 조항이 특약마다 반복되므로 이건 심각한 오정위였다 — required 415 그룹 중 **152개(37%)**의
앵커가 코퍼스에 6회 이상 등장했다.

```
"다음각호의사유가발생한경우이특약은그때부터효력이없습니다"       157회
"특약보험료납입기간중주계약의보험료납입이면제된경우…"           140회
"이특약의피보험자가특약보험기간중사망한경우에는…"                75회
```

질문은 특정 특약을 묻는데 gold 는 문서 앞쪽 아무 특약의 같은 조항을 가리켰다. 게다가 head25 스팬은
길이 25자라 `OCC_MIN=40` 미만이어서 동일문구 확장에서도 빠졌다 — 가장 모호한 것이 구제도 못 받았다.

**수정**: `locate_all()` 이 **모든 출현**을 돌려주고, 질문이 특약을 지정하면 그 scope 로 좁힌 뒤
나머지를 전부 OR 멤버(`src="same_quote"`)로 넣는다. 멤버/그룹이 1.38 → **10.18** 로 늘었다.

효과: R@5 **.2563 → .3738**, R@10 .3355 → .5138, R@40 .5332 → .6957.

### 4.2 융합을 조 단위로 접고 하면 오른다 (+3.8pp)

`run_v7.py` 는 `union_rank(rows, ...)` 로 **태그 채널의 element 순위**를 RRF 에 넣는다. 같은 조에 여러
element 가 매핑되면 그 조의 순위가 희석된다. 조로 먼저 접은 뒤 융합하면 개선된다.

| 융합 방식 | R@5 | R@inf |
|---|---:|---:|
| element 순위로 융합 (구 `run_v7`) | .3738 | .9367 |
| **조 단위로 접고 융합 (현행, k=60 1:1)** | **.4068** | **.9855** |

**`run_v7.py` 에 반영 완료** — `union_rank()` 가 조 단위로 접힌 순위 목록을 받는다.
`--rrf-k` / `--w-tag` / `--w-meta` 를 인자로 노출했다.

**파라미터는 레버가 아니다.** 조 단위 융합 위에서 `rrf_k` ∈ {5,10,20,40,60,90,120,200} × 가중 4종을
스윕해도 현행 k=60 1:1(.4068) 대비 최고 k=40 1:1(**.4124**), **+0.6pp** 에 그친다.

정리하면 융합 단계에서 얻을 수 있는 것은 **조 단위 접기 +3.3pp, 파라미터 +0.6pp** 로 합쳐 약 4pp 다.
90%까지 남은 약 49pp 는 각 채널이 후보를 어떤 **순서**로 내놓느냐에 달려 있다.

## 5. 기존 발표치 .53 과의 차이는 gold 도 실행도 아니고 **문항 구성**이다

"v7 수치가 과거 실험보다 너무 낮다"는 의문을 세 갈래로 검증했다.

**(1) gold 는 정상이다.** 같은 예측을 세 gold 에 각각 채점(공통 122문항):

| gold | 그룹/문항 | R@5 | R@10 | R@40 |
|---|---:|---:|---:|---:|
| v7 strict | 2.25 | .3484 | .5030 | .6810 |
| v4 train | 2.42 | .3570 | .4666 | .6586 |
| u3 overlay | 1.38 | .3306 | .4577 | .6257 |

세 gold 가 사실상 같은 값을 낸다. v7 이 부당하게 엄격한 게 아니다.

**(2) 실행도 정상이다.** 같은 gold(v7 strict) · 같은 163문항:

| 예측 | R@5 | R@10 | R@40 |
|---|---:|---:|---:|
| 이번 실행 (luna qtags, limit 2000) | **.3737** | .5187 | .7027 |
| 아카이브 0823 union (haiku qtags) | .3615 | .5096 | .7061 |

이번 실행이 오히려 근소하게 낫다. 회귀가 아니다.

**(3) 차이는 전부 문항 구성이다.** 아카이브 예측 · v4 gold 로 채점하되 v7 포함 여부로만 분리:

| 구간 | n | 그룹/문항 | R@5 |
|---|---:|---:|---:|
| **v7 에 포함된 문항** | 163 | 2.31 | **.3722** |
| **v7 이 버린 문항** | 174 | **1.08** | **.6772** |
| 전체 (= 기존 발표치 .5297) | 337 | 1.67 | .5297 |

**기존의 .53 은 정답이 사실상 1개뿐인 174문항(.68)이 떠받치던 값이다.** 그 174문항은 v3 계보의
"1-best 절단" gold 를 쓰고, v7 은 현업 답안지가 확정한 문항만 남겼는데 그쪽이 다중근거 위주다.

→ **과거 수치와 v7 수치를 같은 표에 놓지 말 것.** 검색기 성능 변화가 아니라 문제 난이도 변화다.

## 6. 이전 계보를 왜 못 쓰는가

**v3 (`gold_mapped_noah_v3_*`) — 채점 우주 파손.** gold의 `e#####` 433개가 전부 `elements_u2.jsonl`에 같은 문자열로 존재해서 `set&set` 채점이 에러 없이 돌지만, 실제 스팬 겹침은 **466개 중 0개**. `e07495`는 질문이 "척추 장해 장해분류표"인데 본문은 `"대장점막내암"의 정의`, `e07574`는 "1~5종 수술분류표"인데 `민법 제1001조(대습상속)`이다. 약 7,900단위 우주의 인덱스를 32,366개짜리 u2로 읽어 **약 4.4배 압축**된 결과다. v3는 자기 자신의 span gold와도 100% 불일치한다.

**v4 (`out/noah/gold_v4_*`) — train의 절반이 v3 레거시.** 337건 중 **165건(49%)이 `gold_src=v3`** 로 `jos`가 없어 j-ID 채점에서 자동 recall 0. test 90은 깨끗.

**u3 overlay281 — 문항당 근거 1.20개.** v3의 1-best 절단을 물려받았다. R@5 산술 상한이 1.0인 이유가 "정답이 하나뿐이라서"다.

**v6 — 문항당 required 4.09개.** 답안지에 충실하지만 5칸에 3.7개를 넣으라는 요구가 되어 R@5 목표와 맞지 않는다(융합 arm R@5 .2611, 산술 상한 .9431).

## 7. 주의사항

1. **ID는 반드시 `elements_u2jo.jsonl`로 풀 것.** 같은 j-ID를 u3jo로 풀면 R@5가 .587 → .178로 무너진다.
2. **`status=="ok"`를 품질 게이트로 쓰지 말 것.** v4에서 427/427이 ok였고 v7도 전부 ok다. 실제 품질 축은 `partial`과 `grade`다.
3. **partial 77건(28%)은 recall을 과대평가한다.** 코퍼스 밖 인용은 gold에 못 담아 분모에서 빠진다. 층위를 갈라 병기할 것.
4. **required/supporting은 자동 초벌 + usage 순위다.** 명세 §2는 "최종 등급은 사람 판정이 우선"이라고 명시한다. 강등된 521건 중 표본 검수가 필요하다.
5. **정위 앵커는 상용구를 물 수 있다.** §4.1 의 수정으로 동일 인용의 모든 출현을 OR 로 넣었지만, 질문이 특약을 지정하지 않으면 좁힐 수 없다(scope 검출은 19문항뿐). head25 로만 잡힌 240건은 여전히 위험하므로 표본 검수가 필요하다.
6. **평가는 융합 arm 하나로만 한다.** 단일 채널(태그만/메타만) 실측은 하지 않는다(2026-08-24 지시).
7. **문서보강 200문항 미포함.** `신뢰도=검수필요`이고 출처가 문단 덤프라 gold 경계가 헐겁다. 검수 공정 설계 후 확장할 것.

## 8. 사용법

```bash
cd docs/0824/new

python build_gold_v7.py                                    # 재빌드 (약 3분)

EMBED_ENDPOINT=http://127.0.0.1:8102/v1 python run_v7.py   # 융합 재실행+채점
python eval_v6.py --pred <예측.jsonl> --gold out/gold_v7_train_lenient.jsonl --sweep
python eval_v6.py --pred <예측.jsonl> --depth 5
```

`--field`로 랭킹 필드 지정 가능(기본은 `ranked_jo` → `jo_top` → `ranked_element` → `u2_top` → `submitted` 자동 탐지).

**보고 규약**: 모든 수치에 `n`, gold 파일명, `strict`/`lenient`, depth를 병기한다. 서로 다른 gold의 수치를 한 표에 놓지 않는다(0817 교훈 — 분모가 다르면 결론이 뒤집힌다).
